# Interview and Job Readiness

## Apply when evidence is sufficient, not perfect

Begin applications when you meet roughly 70% of the core requirements and can show
credible evidence for the highest-priority skills. “Entry level” may still request
experience; internships, open source, freelancing, volunteering and substantial
projects can provide relevant evidence, but represent them honestly.

## GitHub readiness

- [ ] Profile bio states target area and contact method.
- [ ] Three strongest repositories are pinned.
- [ ] Every pinned repository has a clear problem, demo, setup and results.
- [ ] Commits show iteration rather than one generated dump.
- [ ] Tests/CI pass.
- [ ] No secrets, private data or unexplained large files.
- [ ] Third-party code/data are credited and licensed correctly.
- [ ] Issues/roadmap show thoughtful next steps.

## Resume readiness

- [ ] One or two pages appropriate to market and experience.
- [ ] Official titles and dates are accurate.
- [ ] Skills are supported by project/work evidence.
- [ ] Bullets state action, technical decision and measurable result.
- [ ] Target-role keywords are used naturally.
- [ ] Certificates are labeled accurately.
- [ ] No fabricated users, accuracy, savings or production impact.
- [ ] Links are clickable and public.

## Practice questions

### Python

1. When would you use a list, set, dictionary, iterator or generator?
2. How would you process a file larger than memory?
3. What should be unit tested versus integration tested?
4. How do you handle configuration and secrets?
5. Diagnose a small failing function from a stack trace.

### SQL

1. Explain inner versus left join and how duplicates affect row counts.
2. Find the top three products per category using a window function.
3. Calculate month-over-month change.
4. Find users with no orders.
5. Diagnose a query that double-counts revenue.

### Data and ML

1. Design a validation split for time-dependent or grouped data.
2. Give three examples of leakage.
3. Choose a metric for an imbalanced alerting system.
4. Explain calibration and threshold selection.
5. Diagnose high training and low validation performance.
6. Decide whether ML is necessary.

### AI/LLM systems

1. How do you evaluate retrieval separately from generation?
2. How do you make citations verifiable?
3. What is prompt injection and where are trust boundaries?
4. When would you use prompting, RAG or fine-tuning?
5. How do you control cost, latency, privacy and unsafe tool actions?

## Project deep-dive structure

Prepare 2-, 10- and 30-minute versions:

1. user/problem and why it matters;
2. constraints and non-goals;
3. data and risks;
4. baseline;
5. architecture and decisions;
6. evaluation and errors;
7. production/safety considerations;
8. result, failure and next experiment.

## Application system

Track:

- company, role, location and source;
- must-have and preferred skills;
- evidence link for each core skill;
- resume version;
- contact/referral;
- application/interview dates and stages;
- questions/failures;
- follow-up and next action.

Every 20 suitable applications, review:

1. response rate;
2. where rejection occurs;
3. repeated missing skill;
4. weak evidence or positioning;
5. market/eligibility constraints;
6. one experiment for the next batch.

## Honest experience language

Use “built,” “evaluated,” “deployed as a demo,” “tested with N users,” or “used by
the training team” only when true. Do not call a notebook production, a course
exercise research, or an unmeasured claim a percentage improvement.
